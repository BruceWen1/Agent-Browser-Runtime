# Agent Browser Runtime（ABR）— 技术架构与实施方案

> 版本：v1.0 · 设计状态：Implementation Ready（需逐里程碑实施和验证） · 日期：2026-10-10  
> 配套需求：《01_RPD_产品需求与研发定义.md》；任务入口：《CODEX_START_HERE.md》。  
> 规则：**此技术方案定义可实施契约，不代表 Chromium 补丁已编译或各平台输入后端已测试。** 未经实际测试的行为均属于待验证假设。

## 0. 技术结论及不可越过的边界

1. **三条路线共用一个抽象运行时，不复制三套业务框架。** A=官方 Playwright Compatible；B=外部 Native GUI；C=Chromium Native Observer + 原生输入。
2. **“同名 API”与“相同 GUI 事件”是不同保证。** A 模式保留原 Playwright 语义；B/C 中可执行交互依照原生 UI 路径；相同名字的动作可以返回不同 `executionPath`。
3. **B 模式是 C 模式的基础。** C 优先新增浏览器进程只读观察、标签管理和受控 IPC，不在 Chromium 里重新实现可由 OS 输入后端承担的操作。
4. **A1 特征修正与 A2 命令重定向属于研究支线。** 不默认修改 Blink 的可信事件规则，不以篡改浏览器安全状态或规避第三方保护为交付标准。
5. **真正的 GUI 输入对照必须在图形桌面测试。** Headless、纯 DOM 脚本、CDP 输入和 OS 系统输入不得无条件互相代替。
6. **所有外部网页内容视为不可信。** 页面文本不得控制本地文件、权限设置、浏览器升级或 IPC；敏感动作须明确授权。

## 1. 总体拓扑

```text
                 External Playwright code          MCP Client / AI Agent
                           |                              |
                   [Compatible API]                 [MCP Tool API]
                           |                              |
                           +------------+-----------------+
                                        |
                               ABR Application Layer
                    +-------------------+-------------------+
                    | Session Manager / Capability Registry |
                    | Policy / Approvals / Audit / Artifacts |
                    +-------------------+-------------------+
                                        |
                              Engine Dispatch / Adapters
                    +-------------------+-------------------+
                    |                   |                   |
              A: Compatible        B: GUI            C: Native
              official PW          DesktopAgent      Chromium Observer
                    |                   |                   |
              Playwright CDP       OS AX/Screen      Chromium //chrome
                    |              OS Native Input       readonly bridge
                    |                   |                   |
                    +-------------------+-------------------+
                                        |
                                Chrome / Chromium
                                        |
                                      Website
```

**解释：** 外部 Playwright 应用仍可以直接调用官方包；ABR 的 Compatible Worker 可以将其作为一个后端，但**不宣称 ABR MCP 覆盖官方 Playwright 的每一个方法**。直接运行原脚本与使用 ABR 的 MCP 工具是两种入口，均遵循同一个 Profile/版本/策略协议。

### 1.1 进程划分

| 进程 | 技术 | 边界 | 启动方式 |
|---|---|---|---|
| `abr` CLI | Node.js/TypeScript | 诊断、配置、打包入口 | 用户启动 |
| `abr-mcp` | MCP SDK v2/TypeScript | MCP stdio，调用 Runtime Core | MCP Host 启动 |
| `abr-core` | TypeScript 库 | Session/Policy/Capability/Artifact/Logger | 被 `abr-mcp`/CLI 调用 |
| `abr-pw-worker` | Node.js + 官方 Playwright | 独立运行 Playwright，管理浏览器上下文 | Core 子进程 |
| `abr-desktop-agent` | Rust | OS 级截图、无障碍、窗口、鼠标、键盘 | Core 受控子进程 |
| `abr-chromium-bridge` | Chromium `//chrome/browser` 内部 C++ | Native 只读观察与窗口管理 | Native Chromium 进程内部 |
| `abr-fixture` | 本地 HTTP 服务/TypeScript | 本地对照测试网页与事件记录 | 测试套件 |

`abr-core` 不依赖浏览器私有 C++ 头文件；`abr-desktop-agent` 不直接连接公网；`abr-chromium-bridge` 不直接提供远程 MCP 接口，避免在 Chromium 进程内实现过多应用层逻辑。

### 2.1 技术栈（冻结原则）

- Node.js LTS + ESM TypeScript，MCP 使用 **`@modelcontextprotocol/server` v2**；引入 `zod/v4`（或 v2 SDK 支持的 Standard Schema 适配层）。官方 v2 当前稳定、符合 MCP 2026-07-28 规范。
- `pnpm` workspace 管理 TS 包；新增依赖时使用精确版本并提交 lockfile，不在本文虚构尚未核对的版本号。
- Rust stable 实现 OS 输入与 AX 接口；通过 feature-gated 后端编译 Windows/macOS/Linux。Rust crate 版本在首个兼容性提交中固定。
- 测试：Vitest（核心与契约）、官方 Playwright（本地 fixtures）、Rust `cargo test`、Node MCP Inspector、各 OS GUI 集成测试。
- 只读状态与操作指令使用 schema-first；日志采用 JSON lines，trace 使用具版本号的规范化 JSON。
- 错误、会话、能力 schemas 为独立包；**禁止**在 MCP、CLI、Agent 之间各自复制数据定义。

### 2.2 模块依赖约束

`mcp-server → core → (playwright-worker | native-ipc-client)`；`cli → core`；`native agent` 不得依赖 Node 库；`chromium-bridge` 不得依赖 MCP SDK。

静态检查：如 `packages/core` 引入 `playwright`，或 `packages/mcp-server` 直接调用 Windows/AX API，则 CI 失败。

## 3. 统一 Browser API 与数据契约

### 3.1 数据类型（TypeScript 规范草案，必须实现在 `contracts/browser-api.ts`）

```ts
export type Engine = 'compatible' | 'gui' | 'native';
export type SessionStatus =
  | 'creating' | 'ready' | 'busy' | 'paused' | 'closing' | 'closed' | 'failed';
export type ExecutionPath =
  | 'playwright-cdp' | 'os-input' | 'chromium-observer'
  | 'playwright-script' | 'not-executed';
export type CoordinateSpace = 'viewport-css' | 'window-dip' | 'screen-physical';
export type Capability =
  | 'observe.ax' | 'observe.screenshot' | 'window.focus'
  | 'input.pointer' | 'input.keyboard' | 'input.ime'
  | 'browser.navigate' | 'browser.tabs' | 'browser.fileDialog'
  | 'script.evaluate' | 'network.intercept';

export interface CreateSessionRequest {
  engine: Engine;
  browser: 'bundled-chromium' | 'installed-chrome' | 'custom-chromium';
  profile: { mode: 'ephemeral' | 'persistent'; name?: string };
  headless?: boolean;  // gui/native require false
  locale?: string;
  allowedOrigins?: string[];
}
export interface BrowserSession {
  id: string; engine: Engine; status: SessionStatus;
  browserVersion: string; browserCommit?: string;
  playwrightVersion?: string; platform: string;
  capabilities: Capability[];
  createdAt: string; profileId: string;
}
export interface AxNode {
  nodeId: string; role: string; name?: string; value?: string;
  states: string[];
  bounds?: { x: number; y: number; width: number; height: number;
             space: CoordinateSpace };
  children?: AxNode[];
}
export interface BrowserSnapshot {
  sessionId: string; snapshotId: string; timestamp: string;
  windowId: string; tabId?: string; root: AxNode;
  scale: { dpr: number; zoom: number };
  source: 'os-accessibility' | 'chromium-accessibility'
       | 'playwright-accessibility';
}
export type Target =
  | { kind: 'ax-node'; snapshotId: string; nodeId: string }
  | { kind: 'coordinate'; x: number; y: number;
      space: CoordinateSpace; windowId: string };
export interface ActionRequest {
  requestId: string; sessionId: string; action: string;
  target?: Target;
  args?: Record<string, unknown>;
  timeoutMs?: number;
  expectedSnapshotId?: string;
}
export interface ActionResult {
  requestId: string; actionId: string; sessionId: string;
  status: 'succeeded' | 'failed' | 'approval-required' | 'cancelled';
  executionPath: ExecutionPath;
  startedAt: string; finishedAt: string;
  snapshotIdAfter?: string;
  artifacts?: string[];
  error?: { code: BrowserErrorCode; message: string;
            retryable: boolean; nextAction?: string };
}
export type BrowserErrorCode =
  | 'INVALID_ARGUMENT' | 'SESSION_NOT_FOUND' | 'SESSION_CLOSED'
  | 'UNSUPPORTED_CAPABILITY' | 'PERMISSION_REQUIRED'
  | 'APPROVAL_REQUIRED' | 'POLICY_DENIED' | 'TARGET_STALE'
  | 'TARGET_NOT_FOUND' | 'TARGET_OCCLUDED' | 'FOCUS_LOST'
  | 'DESKTOP_BUSY' | 'INPUT_BACKEND_UNAVAILABLE'
  | 'BROWSER_DISCONNECTED' | 'TIMEOUT' | 'INTERNAL_ERROR';
```

**强制语义：** `snapshotId` 是一次观察结果的版本标识；不是跨导航永久稳定的元素主键。GUI/Native 点击 AX 节点必须重新验证窗口 PID、快照生命周期、可见性、目标边界和前台焦点。如果发现旧快照或元素在当前结构中无法可靠重定位，返回 `TARGET_STALE`，不能以旧坐标直接点击。

### 3.2 核心服务接口

```ts
export interface CapabilityReport {
  supported: Capability[];
  unsupported: Partial<Record<Capability, string>>;
}
export interface BrowserEngine {
  readonly kind: Engine;
  create(input: CreateSessionRequest): Promise<BrowserSession>;
  capabilities(sessionId: string): Promise<CapabilityReport>;
  observe(sessionId: string): Promise<BrowserSnapshot>;
  screenshot(sessionId: string): Promise<{ mimeType: 'image/png'; blobId: string }>;
  execute(input: ActionRequest): Promise<ActionResult>;
  pause(sessionId: string): Promise<void>;
  resume(sessionId: string): Promise<void>;
  close(sessionId: string): Promise<void>;
}
```

业务逻辑只依赖 `BrowserEngine`。所有后台通过统一 `EngineRegistry` 注册，要求 `kind` 唯一、跨语言错误码不漂移。统一适配不代表各引擎自动执行等同的操作，能力检查是强制步骤。`CapabilityReport.unsupported` 必须包含每项已知不可用能力的机器可读原因，不可仅返回一个缺省空数组。

### 3.3 状态机

```text
creating --success--> ready --action--> busy --finish--> ready
     |                  |             |         |
     +--error--> failed |             +--pause->paused
                        +--pause----->paused --resume--> ready
ready/paused/failed --close--> closing --> closed
```

- `busy` 表示存在独占动作；只读 `observe` 可以并行但不得读取“半完成”快照作为可点击引用。
- `paused` 禁止发送系统输入；允许截图、观察、close。
- `failed` 不自动复用旧浏览器进程；用户显式重建会话。
- 每个状态改变写入持久化 audit，不在异常中丢失 `close` 资源释放。

### 3.4 资源与超时

- 每个动作具有唯一 `requestId`（UUIDv7/UUID），每个 Engine 返回 `actionId`；相同 `requestId`、完全相同 payload 在本会话内重复提交时返回既有结果，不能执行第二次点击。不同 payload 使用旧 `requestId` → `INVALID_ARGUMENT`。
- 默认动作超时由配置明确指定；不要在未通过产品评审前使用无限等待。
- 会话、截图和 trace 资源配额可配，内存不足时由队列拒绝而非杀死浏览器。
- `ActionResult.status=succeeded` 只表示受权操作路径已完成，且获得必要的执行后观察；并不等同业务表单已提交或网页任务完成。业务结果须由 `observe`/`wait_for` 或单独声明的断言验证。
- `close()` 幂等；后台释放动作租约、浏览器句柄与临时文件。

## 4. MCP v2 接口

### 4.1 协议与传输

默认 `stdio`：MCP Host 启动 `abr-mcp`，从 stdin 读协议，将 stdout 保留为协议通道，日志只写 stderr。后续如需 Streamable HTTP，必须新立 ADR 审批鉴权、Origin 校验、CSRF、TLS 与审计。此约束与 MCP TypeScript v2 的 server factory 一致。

**v2 SDK 推荐代码形态：**

```ts
import { McpServer } from '@modelcontextprotocol/server';
import { serveStdio } from '@modelcontextprotocol/server/stdio';
import * as z from 'zod/v4';
import { runtime } from './runtime-instance.js';

function createMcpServer() {
  const server = new McpServer({ name: 'abr', version: '1.0.0' });
  server.registerTool('browser_capabilities', {
    description: 'List executable capabilities for a browser session.',
    inputSchema: z.object({ sessionId: z.string().min(1) })
  }, async ({ sessionId }) => {
    const data = await runtime.capabilities(sessionId);
    return { content: [{ type: 'text', text: JSON.stringify(data) }] };
  });
  return server;
}

void serveStdio(createMcpServer);
```

以上为 SDK v2 接口结构示例。实际版本依赖与 TypeScript 编译选项必须在 M0 中进行安装验证并提交锁文件；不要复制 MCP v1 的旧包路径。

### 4.2 Tool 清单及强制校验

| 工具名 | 关键输入 | 输出 | 权限/风险 |
|---|---|---|---|
| `browser_session_create` | engine, browser, profile | BrowserSession | 允许的 Profile 根目录 |
| `browser_session_list` | 空 | session[] | 当前用户所属会话 |
| `browser_session_close` | sessionId | closed | 必须清理资源 |
| `browser_capabilities` | sessionId | capabilities + reasons | 只读 |
| `browser_observe` | sessionId, depth?, filter? | BrowserSnapshot | 隐私过滤 |
| `browser_screenshot` | sessionId, region? | PNG content + blobId | 录屏权限与脱敏 |
| `browser_click` | sessionId, requestId, target | ActionResult | GUI 目标校验 |
| `browser_double_click` | 同上 | ActionResult | 点击状态 |
| `browser_pointer_move` | sessionId, requestId, target | ActionResult | 输入锁 |
| `browser_key_press` | sessionId, requestId, key/modifiers | ActionResult | 键盘布局 |
| `browser_type_text` | sessionId, requestId, text, strategy | ActionResult | 敏感文本策略 |
| `browser_scroll` | sessionId, requestId, deltaX/deltaY | ActionResult | 标定坐标 |
| `browser_drag` | sessionId, requestId, source, destination | ActionResult | 捕获失败诊断 |
| `browser_navigate` | sessionId, requestId, url | ActionResult | Origin 策略 |
| `browser_go_back` | sessionId, requestId | ActionResult | 历史状态 |
| `browser_switch_tab` | sessionId, requestId, tabId | ActionResult | 会话内标签 |
| `browser_choose_file` | sessionId, requestId, filePath | ActionResult | 显式授权+路径校验 |
| `browser_wait_for` | sessionId, target/state/timeout | WaitResult | 观察，不改网页 |
| `browser_approval_status` | approvalId | approval state | 只读；批准在本地 UI 完成 |
| `browser_trace_export` | sessionId, format | artifactRef | 导出敏感信息时校验 |

注意：审批决定只能通过本地可信 UI/本地用户会话专用 IPC 触发，不提供 `browser_action_approve` MCP 工具。**不得**把自我授权能力暴露给同一个 AI 模型并视其为用户确认。MCP 模型端请求敏感动作时返回等待批准结果，由本机独立审批 UI 完成。

### 4.3 MCP 响应语义

- 业务成功：`ActionResult.status=succeeded`；同时返回 JSON 结构化内容和简短文本摘要。
- 可预期失败：返回正常 MCP tool result，设置 `isError: true` 并包含 `error.code`；不要令服务器进程崩溃。
- 只有 JSON-RPC 无法解析、无效方法、传输错误等才返回协议级 error。
- `browser_screenshot` 小图可以输出 MIME=image/png 的 MCP 内容块；较大文件返回 `blobId` 并用受控 `browser_artifact_read` 按权限读取。禁止直接回传浏览器完整用户目录。
- 工具名以 `browser_` 前缀，命名稳定；变更输入/输出 Schema 应升级 API major version。

### 4.4 典型创建—操作—验证时序

```text
client -> MCP: browser_session_create(engine=gui, profile=ephemeral)
MCP -> Core: policy.check / registry.create
Core -> DesktopAgent: start / permissionCheck / attachChromeWindow
Core -> MCP: BrowserSession(ready, capability list)
client -> MCP: browser_observe(sessionId)
Core -> DesktopAgent: captureAX; [snapshot=s1]
client -> MCP: browser_click(target={snapshotId:s1,nodeId:n7})
Core -> Policy: check origin + action authorization
Core -> DesktopAgent: verify target; acquire foreground lease
DesktopAgent -> OS: move pointer; down; up
Core -> DesktopAgent: observe new snapshot s2
Core -> MCP: ActionResult(succeeded, executionPath=os-input)
```

## 5. 安全模型和权限设计

### 5.1 信任边界

```text
Untrusted website/DOM ---------> Browser rendering process
          X    cannot invoke IPC or MCP commands
Trusted local user -----------> Approval UI / config
MCP client (limited trust) ----> PolicyEngine ----> BrowserEngine
Native OS permissions --------> DesktopAgent
```

- 网页可访问文本、DOM 和 AX 节点内容均是**数据**而非指令。禁止把网页中“请运行命令/上传文件/忽略规则”当作系统命令。
- MCP Client 即使来自本地，也不能越过用户明确配置的域名、文件目录与敏感操作策略。
- Browser Engine 不向网页暴露隐藏本地 token、IPC socket、daemon 文件路径；Chromium Native Bridge 不暴露 `window.*` JS API。
- `CreateSessionRequest.allowedOrigins` 只能**收窄**系统/用户已设置的 allowlist，不能由 AI 扩大授权范围；`policy.requireHumanApproval` 不得因会话请求而禁用。

### 5.2 权限分级

| 级别 | 示例 | 默认策略 |
|---|---|---|
| read | observe、screenshot | 允许，仅对授权会话；隐私遮盖 |
| navigation | 打开 URL、切换标签页 | Origin allowlist 校验 |
| action | 点击、输入、滚动 | 允许在受权域上执行；敏感控件需额外审批 |
| elevated | 上传文件、发送消息、删除、付款 | 强制人工批准；业务敏感性须由可信策略或用户意图明示，通用点击不能自动可靠判定全部付款操作 |
| debugging | Evaluate、request interception、CDP inspect | Compatible 专属，默认不作为 MCP 工具开放 |

### 5.3 Profile 与目录

- 用户数据目录由 ABR 管理，根路径在用户应用数据目录下，路径必须规范化并限制在 `profileRoot` 内。
- Chrome 136 起，远程调试端口/管道不能使用默认 Chrome 用户数据目录；Compatible 的独立 Profile 必须遵循此约束。
- `ephemeral` 在关闭后清理，`persistent` 仅保留经过标记的用户 Profile；不同时启动共享 Profile 的多个浏览器实例。
- 密码输入、登录信息、Cookie、授权 token 不写日志；屏幕截图受保存期限和开关控制。

### 5.4 Local IPC 安全

`abr-core` 与 Rust Agent 采用进程间本地传输：Windows Named Pipe（按当前用户 SID 设置 ACL），Unix 使用 `0600` 的 UDS 和权限受限的 runtime 目录。双方用启动期间通过受保护 IPC/继承句柄传入的临时 session secret 做每连接握手；不得将 secret 置于日志、URL、进程命令行参数。

框架约束：单帧最大 4 MiB（可配置但受硬上限保护）；先读长度再解析 JSON；超限直接断开；每个客户端有 request rate 和并发限制；不接受来自非授权用户的连接；所有消息都带 requestId、schemaVersion、sessionId。

### 5.5 OS 安全边界

- Windows：`SendInput` 受 UIPI 约束；不得通过提升为系统权限或关闭安全机制绕过。
- macOS：AX 与屏幕录制依赖用户在系统设置中明确授权；不得试图无提示授予。
- Linux Wayland：必须使用桌面门户授权的 RemoteDesktop/ScreenCast/libei 通路，若 Portal 无输入后端则明确 `INPUT_BACKEND_UNAVAILABLE`。
- 依赖文件上传选择器/剪贴板等敏感操作时，需保证明确用户授权及路径范围限制。

## 6. `compatible` 引擎：保留官方 Playwright

### 6.1 两种连接模式（必须分开标注）

**P1：原生 Playwright launch（默认）**：由 `abr-pw-worker` 使用锁定官方 Playwright 版本启动捆绑匹配 Chromium 或定制可执行文件。可选 `headless:false`；原版 API 行为保持。BrowserContext 与 Profile 符合 Playwright 原有设计。

**P2：`connectOverCDP`（实验/降级）**：连接已有 Chromium/Chrome；官方文档说明它比 Playwright 协议连接的保真度显著较低。必须在能力矩阵中标记，不能声称与 P1 等价。

```ts
// packages/playwright-worker/src/launch.ts
import { chromium, type Browser } from 'playwright';

export async function launchCompatible(
  executablePath?: string
): Promise<Browser> {
  return chromium.launch({
    headless: false,
    ...(executablePath ? { executablePath } : {})
  });
}
```

**直接使用者的升级路径**：官方脚本保留对 `playwright` 的 import，通过 ABR 配置生成匹配的 `launchOptions` 或连接清单；不得承诺不改任何调用即可在已有 Playwright 脚本中替换浏览器，除非产品专门实现且测试了注入/适配方式。

### 6.2 CompatibleWorker 具体责任

- 维护 sessionId 与 Playwright Browser/Context/Page 映射，保证进程内的错误隔离。
- 输出 `executionPath='playwright-cdp'`；若使用 `locator.evaluate` 等脚本路径，输出 `'playwright-script'`。
- 提供 MVP 的 navigate、screenshot、click、type、scroll、switchTab；所有方法通过官方 API 实现。
- 提供 Playwright 版本及 Browser 版本信息；卸载/退出时 close browser/context；按需保留 trace。
- 不能在 Worker 中擅自修改 `navigator.webdriver`、Canvas、WebGL、DOM Prototype 或注入隐藏指纹脚本。

### 6.3 A1：特征差异研究工作台

- 把原版 Chrome GUI（A）、原版 Playwright（B）、同 commit 定制 Chromium GUI（C）、定制 Chromium + Playwright（D）的页面可观察轨迹并排比较。
- 只允许选择经复现的问题建立独立 Patch ID 与开关。任何补丁须注明“观测差异”“变更语义”“可能影响的 Web 标准/权限/安全机制”“三个平台的回归用例”。
- 不全局改写可信事件、安全权限、TLS、指纹；不能仅凭一个第三方“检测评分”上线补丁。
- 支线交付是证据、风险、测试和可复现 Patch，而不是对任意第三方网站的通过率承诺。

### 6.4 A2：Playwright 指令重定向研究

- 首先审计哪些 API 在协议层具备明确输入含义，如 CDP `Input.dispatchMouseEvent`、`Input.dispatchKeyEvent`；哪些操作使用脚本/DOM 机制，如 `selectOption`、`evaluate`。
- 对可以无歧义地表达为 GUI 的操作，可在**独立 prototype** 验证“CDP 输入命令 → 系统 GUI 输入服务”所产生的事件及回调结果；必须解决坐标体系、窗口焦点、输入顺序、同步和多进程时序。
- 对没有 GUI 含义的 `evaluate`、route、浏览器上下文权限改写，不做通用重定向；保留原语义并标记 `not-gui-equivalent`。
- A2 研究不阻塞主干升级和三平台安装包；禁止默认开启，必须记录到 ADR 并通过全量回归后再考虑产品化。

## 7. `gui` 引擎：外部系统 GUI 控制

### 7.1 Observation 与 Action 分离

Observation：读取 Chrome 应用窗口树、AX 节点、标题/角色、屏幕边界、屏幕截图；不通过 UIA `InvokePattern` 或直接修改 DOM 实施交互。

Action：读取当前前台 Chrome PID，聚焦窗口、获取系统输入锁、操作鼠标/键盘/滚轮、释放输入锁、重新观察验证结果。

**不要用 `AXPress`、UIA `InvokePattern` 或 `ValuePattern` 直接代替物理点击/键入**，除非作为单独的非 GUI 语义能力被明确标注和测试；V1 的 GUI 模式以 OS input path 为主。

### 7.2 平台后端抽象（Rust）

```rust
pub trait DesktopBackend {
    fn list_browser_windows(&self) -> Result<Vec<WindowInfo>, BackendError>;
    fn focus_browser_window(&self, window_id: &str) -> Result<(), BackendError>;
    fn get_accessibility_tree(&self, window_id: &str) -> Result<AxSnapshot, BackendError>;
    fn capture_window(&self, window_id: &str) -> Result<ImageBlob, BackendError>;
    fn pointer_move(&self, x: i32, y: i32) -> Result<(), BackendError>;
    fn pointer_button(&self, button: MouseButton, down: bool) -> Result<(), BackendError>;
    fn keyboard_key(&self, key: KeyDescriptor, down: bool) -> Result<(), BackendError>;
    fn wheel(&self, delta_x: i32, delta_y: i32) -> Result<(), BackendError>;
    fn get_permissions(&self) -> Result<PermissionReport, BackendError>;
}
```

该接口是设计契约，Rust 具体 `Send/Sync`、异步与生命周期由 M2 实现时统一调整；但不得在各平台改动 JSON schema 或错误语义。输入坐标必须先由 Core 转换为 `screen-physical`，并带显式 `windowId` 防止误操作其他应用。

### 7.3 Windows 实现规范

- 无障碍：UI Automation COM (`IUIAutomationElement`)，通过进程 ID 定位属于 Chrome 的顶层窗口，按需读取 `ControlType/Name/BoundingRectangle/IsEnabled` 等属性。
- 输入：Win32 `SendInput`，分别发送鼠标移动、button down/up、按键 down/up；检查返回插入事件数量和错误。对键盘使用扫描码/布局映射的合适方式；区分 Unicode/IME/物理键语义。
- 窗口：Win32 HWND、PID、前台窗口；多显示器、负坐标、DPI Awareness；防止窗口遮挡与焦点变化。
- 截图：优先采用兼容现代 GPU 桌面的捕获路径，运行时 capability detection；不能依赖对所有窗口都有效的单一 BitBlt 技术。
- 权限：遵守 Windows UIPI；不尝试越过高完整性程序。
- 最低验收：多显示器、125% DPI、中文/英文输入、Tab 焦点、Chrome 地址栏、上传选择器，以及输入竞争与焦点抢占。

### 7.4 macOS 实现规范

- 观察：`AXUIElementCreateApplication(pid)` + AX 属性读取；为 AX API 设置合理 timeout 与可中断机制，避免无响应应用使 daemon 永久阻塞。
- 输入：Quartz CGEvent / 系统事件派发；与实际键盘布局/Command 修饰键配合，文本输入与 IME 单独处理。
- 截图：ScreenCaptureKit 或官方支持的屏幕捕获 API；用户未授予录屏权限时返回 `PERMISSION_REQUIRED`。
- 窗口：应用 PID、窗口 ID、前后台切换、Retina 坐标转换；使用 `CGWindow`/Accessibility 获取窗口位置信息时比较精度与隐私权限。
- 签名：交付安装包考虑 Apple notarization、公证和 TCC 授权持久化；不能通过无签名开发环境的权限表现推断正式包行为。
- 最低验收：Apple Silicon、Retina、Command+快捷键、日文/中文 IME、文件选择器及权限撤销后的回退行为。

### 7.5 Linux X11 实现规范

- 观察：AT-SPI2 服务（D-Bus），结合窗口管理器 API 获取 Browser window bounds。
- 输入：X11 原生输入（XTest 等）或桌面允许的模拟输入 API；记录窗口系统为 `x11`，不得错误标记为 Wayland。
- 截图：X11 截图或 Desktop Portal 截图；支持 Chrome GPU 合成情况下窗口快照。
- 窗口与焦点：EWMH/WM 约束，使用 X11 前台窗口状态判断；生产不能假定无窗口管理器的纯 Xvfb 等同真人 GUI。
- 首发参考环境：Ubuntu LTS x64 X11；记录实际系统版本、WM、缩放、输入法以构成测试基线。

### 7.6 Linux Wayland 实现规范

- 观察：AT-SPI + ScreenCast Portal，用户授权屏幕/窗口捕获。
- 输入：RemoteDesktop Portal 获得受控会话，优先 `ConnectToEIS()` + libei；或平台门户支持的输入方法。其 API 依赖桌面环境后端，不应假定所有 Wayland 桌面均支持。
- 不在未授权环境使用 `/dev/uinput`、root 提权等全局输入绕过作为默认后端。
- `abr doctor` 输出 Portal 类型、后端、session permission、是否存在输入能力、失败原因；能力不足时标记 `input.pointer/input.keyboard` unsupported。

### 7.7 目标定位策略

1. `observe` 获取快照并检查 `windowId`/PID/scale。
2. Agent 选择 `AxNode`；在点击前验证节点仍存在、可见、可交互、未被另一个窗口遮挡。
3. 把 `viewport-css` 或 `window-dip` 转换为 `screen-physical`；所有坐标必须标注空间，禁止直接把 CSS 像素当物理像素。
4. 使用输入队列派发 pointer/keyboard；严格保持 down/up 成对。
5. 执行完 capture 新快照，比较预期条件（如按钮激活、导航、焦点变化），不可仅因为输入函数没有异常就宣告成功。
6. 页面未达到期望结果时，只允许按照动作可幂等性进行受控恢复；不可自动重复付款/提交/删除等非幂等动作。

### 7.8 键盘输入分三类

| 类型 | 语义 | API 设计 |
|---|---|---|
| `key-press` | 按键及修饰键事件 | `browser_key_press` |
| `type-text` | 用户可读字符串提交 | `browser_type_text`，返回 actualStrategy |
| `ime-composition` | 依赖系统输入法组合文本 | 可选扩展，平台 capability-gated |

不要将 Windows `KEYEVENTF_UNICODE`、macOS 文本提交、Linux X11 keysyms 与物理扫描码按键宣称绝对相同。报告实际执行策略，并针对 `keydown/beforeinput/input/composition*` 独立测试。

### 7.9 GUI 线程所有权与并发

一个 OS desktop seat 在任何时刻只有一个 `DesktopInputLease`：`(seatId, sessionId, leaseId, expiry)`；lease 获取后重新验证前台目标 PID；若用户主动输入、其他应用抢焦点或窗口关闭，立即中止后续输入并释放 lease。多 GUI 会话可读取页面，但不可同时注入输入。Compatible 的后台并发另行管理，不分享这把 OS 级锁。

## 8. `native` 引擎：Chromium 浏览器内集成

### 8.1 实施原则

- **第一版只读、只浏览器层。** `//chrome/browser` 注入观察服务而不是在 Blink/V8/Network Service 中修改浏览器网页行为。
- 复用 Chromium 的 Browser/AxTree 缓存，经过浏览器进程权限检查后将节点快照传给 ABR；只提供必要字段，不提供 cookies/passwords 等敏感浏览器存储。
- `native` 引擎调用 GUI Agent 的系统输入后端完成点击键入；如果要添加 Chromium 内部输入分发，必须建立独立 API 名称与 GUI 等价验证。
- `bridge` 的 IPC 限制在当前用户与指定浏览器进程，且只对 ABR 创建/显式授权的 Profile 生效，不能被网页 renderer JavaScript 直接访问。

### 8.2 Browser Bridge 最小接口

```text
NativeObserver/v1
  hello(nonce, protocolVersion, browserCommit) -> metadata
  listWindows() -> windows[]
  listTabs(windowId) -> tabs[]
  readAccessibility(tabId, limit, treeDepth) -> AxSnapshot
  getViewportMetrics(tabId) -> {zoom, dpr, windowBounds}
  getState() -> {browserVersion, commit, featureFlags}
  subscribe(eventTypes) -> tab/window/AX change notifications
```

**明确禁止**：在 Native Observer 暴露任意脚本执行、Browser Password Store、Cookie 原文、Chrome Network Service 原始凭据或未经授权的任意文件访问。所有 WebContents 与 AX 数据仍需按照不可信渲染内容过滤。

### 8.3 Chromium 代码位置与维护

`chromium/bridge` 保存新增 C++ 源及 patch，核心在 `//chrome/browser` 与必要的 Mojo/IPC 注册点。不要直接在仓库复制完整 Chromium 源树；版本文件保存上游 commit SHA、对应 DEPS 与补丁校验和。

**M4 必须依赖已锁定具体 upstream commit**，由 Codex 在该 commit 中确认真实的 Browser/AX 接口类名、线程模型和 GN target，再生成 patch；不要提前把伪造路径/内部方法名写成可编译事实。

## 9. Rust/TypeScript IPC 定义

### 9.1 消息帧

二进制 framing：`uint32_be payloadLength + UTF-8 JSON payload`，最大 4 MiB。禁止用换行 JSON 裸拼接存储截图；截图在安全临时存储中通过 `blobId` 索引。请求带 `schemaVersion:1, requestId, method, params`；响应带 `requestId, ok, result|error`。协议内字段名与 TypeScript Contracts 一致；Native Agent 启动时完成受保护 secret 握手。

```json
{
  "schemaVersion": 1,
  "requestId": "a77fbe3d-a91a-4f4c-965d-9e5c1f497cdd",
  "method": "desktop.pointerClick",
  "params": {
    "sessionId": "session-001",
    "windowId": "win-001",
    "target": { "kind": "coordinate", "space": "screen-physical", "x": 400, "y": 250, "windowId": "win-001" }
  }
}
```

IPC 内部方法推荐：`desktop.doctor`、`desktop.listWindows`、`desktop.observe`、`desktop.capture`、`desktop.focus`、`desktop.pointerClick`、`desktop.keyPress`、`desktop.typeText`、`desktop.scroll`、`desktop.drag`、`desktop.chooseFile`、`desktop.cancel`、`desktop.shutdown`。

### 9.2 后端返回结构

```json
{
  "schemaVersion": 1,
  "requestId": "a77fbe3d-a91a-4f4c-965d-9e5c1f497cdd",
  "ok": false,
  "error": {
    "code": "FOCUS_LOST",
    "message": "Chrome window is no longer foreground",
    "retryable": true,
    "nextAction": "browser_observe"
  }
}
```

错误码实现必须有穷举测试；Rust panic 不得直接使 MCP Server 丢失已有会话元数据。崩溃后 Core 记录 worker exit code 和健康状态，并拒绝新的输入操作。

## 11. 事件一致性和差异诊断测试

### 11.1 对照组

| 组别 | 浏览器 | 操作路径 | 目的 |
|---|---|---|---|
| A | 官方 Chromium 相同 commit | 人工 GUI | 原始基线 |
| B | 官方 Chromium 相同 commit | 官方 Playwright | 检出自动化原有差异 |
| C | 定制 Chromium 相同 commit | 人工 GUI | 验证补丁是否影响常规 GUI |
| D | 定制 Chromium 相同 commit | 自动化（PW/Native 分别记录） | 验证定制变化后结果 |

另外为 GUI Engine 单独建立 `A vs OS-input` 对照，不应把系统输入误当 CDP 或人工物理输入。

### 11.2 固定环境参数

测试元数据必须记录：`platform/osVersion/arch/windowSystem/keyboardLayout/ime/monitorDpi/chromeCommit/playwrightVersion/abrVersion/profileId/fixtureVersion/pageUrl`。相同组的初始 Cookie、localStorage、viewport、权限、浏览器焦点、标签数必须一致；否则标记 invalid test 而不是 diff。

### 11.3 事件采集器示例（仅在自有 fixture 页）

```ts
const names = [
  'pointerdown','pointerup','mousedown','mouseup','click','dblclick',
  'wheel','scroll','keydown','keyup','beforeinput','input','change',
  'compositionstart','compositionupdate','compositionend',
  'focus','blur','dragstart','dragenter','dragover','drop'
];
const trace: unknown[] = [];
for (const name of names) {
  document.addEventListener(name, (event) => {
    trace.push({
      type: event.type,
      trusted: event.isTrusted,
      target: (event.target as HTMLElement)?.id || (event.target as Element)?.tagName,
      key: event instanceof KeyboardEvent ? event.key : undefined,
      code: event instanceof KeyboardEvent ? event.code : undefined,
      inputType: event instanceof InputEvent ? event.inputType : undefined,
      button: event instanceof MouseEvent ? event.button : undefined,
      pointerType: event instanceof PointerEvent ? event.pointerType : undefined,
      focus: (document.activeElement as HTMLElement)?.id,
      activation: navigator.userActivation?.isActive,
      historyLength: history.length
    });
  }, {capture: true});
}
(window as any).__getTrace = () => structuredClone(trace);
```

这只是最低限度 fixture，实际还要记录 capture/bubble、Selection、DOM MutationObserver、pointer capture、输入法 composition、URL/history/referrer、`visibilityState`、用户激活 API 调用效果；对日志字段做隐私过滤。

### 11.4 Trace 格式及比较算法

```json
{
  "schemaVersion": 1,
  "fixture": "text-input-en",
  "environment": { "os": "windows", "browserCommit": "<sha>", "engine": "gui" },
  "samples": [
    { "type": "keydown", "trusted": true, "key": "a", "focus": "q" },
    { "type": "beforeinput", "trusted": true, "inputType": "insertText", "focus": "q" }
  ],
  "outcome": { "inputValue": "a" }
}
```

比较器分三层：

1. **确定性字段**：事件类型与顺序、`isTrusted`、`inputType`、焦点迁移、用户激活、最终 DOM/Selection；预期一致或给出明确差异解释。
2. **允许归一化字段**：毫秒时间戳、Pointer 路径的连续采样数量（用户已明确排除人的行为节奏），但不可归一化掉缺失的 `keydown` 或错误的 `isTrusted`。
3. **平台相关字段**：键盘 code/layout、IME、缩放、原生对话框事件，仅与同 OS 基线比较。

输出 `identical / accepted-diff / unexpected-diff / unsupported / invalid-fixture` 五种状态，并保存最小重放步骤、对应目标和浏览器版本。

### 11.5 Fixture 覆盖清单

`click-button`、`double-click`、`checkbox-radio`、`text-input-en`、`text-input-cjk-ime`、`textarea`、`select-native`、`date-time`、`file-dialog`、`drag-drop-html`、`scroll-nested`、`iframe`、`shadow-dom`、`popup-user-activation`、`tab-visibility`、`back-forward-bfcache`、`clipboard-permission`、`download`、`upload-confirm`、`focus-navigation`、`touch-when-supported`。

### 11.6 回归阈值与流水线

- 新建 baseline 只能经人工审批，不能由测试失败自动覆盖。
- 每个 P0 操作至少包含 success、permission denied、stale target、focus stolen、cancelled 五类测试之一，整体契约覆盖率不低于全部 P0 行为。
- 完成一组完整 test run 后输出 `parity-report.json`、`parity-report.html`、trace 和版本 manifest。
- 不对“某第三方网站是否封禁”设置发布硬门槛；测试必须基于授权 fixture 和合规的客户环境。

## 12. Chromium 构建、Patch 与升级策略

### 12.1 版本来源与锁定

`chromium/VERSION.lock` 示例：

```yaml
schemaVersion: 1
upstreamTag: "<verified-release-tag>"
upstreamCommit: "<full-40-char-sha>"
playwrightVersion: "<verified-compatible-version>"
patchsetVersion: "0.1.0"
patches:
  - file: patches/0001-bridge-readonly.patch
    sha256: "<computed-sha256>"
targets: [windows-x64, macos-arm64, linux-x64]
```

**不填写未经验证的 Chromium 版本号。** 从官方 Release tag 和对应的 commit 检出，运行 `gclient sync` 同步 DEPS。任何源代码补丁只以 Git patch 形式管理，每条 patch 应有独立的测试链接和风险等级。

### 12.2 原生构建原则

- 使用 Chromium 官方 `depot_tools`、GN、`autoninja`、`fetch chromium`/`gclient sync` 指南；不同 OS 使用官方对应 build instructions。
- Windows 按对应上游版本要求安装 Visual Studio C++ 和 Windows SDK；macOS Xcode/SDK；Linux apt build dependencies。不要在文档中猜测固定工具链可适用于所有 Chromium 发布版。
- M4 构建时 `gn gen out/ABR --args='is_debug=false is_component_build=false symbol_level=0'`，然后 `autoninja -C out/ABR chrome`；具体参数应记录在 manifest 中，调试版另建输出目录。
- 跨平台为原生构建；不依赖从 Windows 机器直接编译所有 macOS 产物。

### 12.3 每次升级的流水线

```text
Detect upstream security/release update
     ↓
Pin commit + DEPS + official release notes
     ↓
Fresh isolated source checkout
     ↓
Apply patch stack with git am --3way (on conflicts: STOP)
     ↓
Build original and patched Chromium for each OS/arch
     ↓
Playwright compatibility smoke + GUI parity A/B/C/D
     ↓
Security review + signed artifacts + staged rollout
     ↓
Record release manifest or reject build
```

所有 patch 冲突、内部接口语义改变、可观察事件差异不明的情况都阻止自动发布；不得自动删除未识别安全检查。升级窗口内可先使用外部 GUI + 正式版 Chrome，避免依赖老旧 Chromium Fork。

### 12.4 版本矩阵

| 组件 | 锁定来源 | 升级原则 |
|---|---|---|
| Chromium | Git SHA、release tag | 每次安全更新单独验证 |
| Playwright | npm exact version + lockfile | 与浏览器组合 smoke tests |
| MCP SDK | npm exact v2 | 协议契约和 host 互通 tests |
| Node/Rust toolchain | `.node-version`、`rust-toolchain.toml` | 分开升级 |
| Native bridge patch | 每 patch SHA256 | 每次升级单独 rebase |
| OS/desktop runtime | release test manifest | 每个 OS 组合可追溯 |

## 13. CI/CD、发布安全与验收

### 13.1 必须的 CI 阶段

1. `lint`：TypeScript ESLint/format/tsc、Rust fmt/clippy；禁止未定义执行路径。
2. `contracts`：MCP schema、IPC schema、错误枚举、配置 schema 的双向解析测试。
3. `unit`：会话、状态机、权限、幂等、坐标转换、artifact TTL。
4. `integration`：FakeBackend 下的 MCP 调用，从 session_create 到 observe/click/close。
5. `compatible-e2e`：官方 Playwright + 本地 fixtures，完整导航/点击/输入/截图。
6. `gui-e2e`：Win/macOS/Linux 独立桌面 runner，真实 Chrome 实机输入测试。无 GUI runner 时状态应为 blocked，不要伪称通过。
7. `native-chromium`：原版与定制版构建、bridge contract、A/B/C/D 差异回归。
8. `security`：依赖审计、漏洞扫描、签名/公证校验、IPC 权限检查、日志脱敏。

### 13.2 软件包发布

- Windows：签名安装包和 CLI；默认不安装系统级驱动。
- macOS：签名/公证 .app/.pkg，提供 Accessibility/ScreenCapture 授权向导。
- Linux：明确支持的发行版包和库依赖，X11/Wayland 能力按平台检测；不默认 root 安装后台服务。
- 附加 SBOM、第三方 NOTICE、`version-manifest.json`、校验和、支持矩阵和升级回滚说明。

### 13.3 发布闸门

任意一个 P0 安全测试失败、Profile 泄漏、MCP 未授权输入、`isTrusted` 等浏览器安全机制被意外改写，或 Chrome 正常浏览模式与定制版产生未解释的回归，均阻止发布。

## 14. 故障处理与可观察性

### 14.1 日志规范

结构化字段：`ts, level, component, sessionId, actionId, requestId, engine, executionPath, durationMs, code, browserVersion, platform`。禁止默认记录文本输入的值、密码、Cookie、文件内容、完整 URL query。

### 14.2 故障恢复策略

| 故障 | 能否自动重试 | 操作 |
|---|---|---|
| AX 引用过期 | 可安全重观察，不自动重复点击 | 返回新快照或 `TARGET_STALE` |
| 焦点丢失 | 无自动输入重放 | 暂停并请求用户恢复 |
| 输入后页面导航超时 | 不重发非幂等动作 | 查询浏览器状态、报告不确定结果 |
| screenshot 权限丢失 | 不自动提升权限 | 提示系统授权 |
| Playwright Worker 崩溃 | 视 Profile 状态重建新 session | 保留 crash audit |
| Chromium bridge 不兼容 | 禁止无提示切换模式 | 报告构建不兼容、引导其他引擎 |

## 附录 A. MCP 机器可读工具契约

`contracts/mcp-tools.json` 列出 21 个工具的 `inputSchema`、对应能力与是否需要人工批准。Codex 在 TASK-002/TASK-006 中应以该文件为审计起点，再转换为官方 MCP SDK v2 的 Zod Schema，生成/测试后保持完全同步。所有工具的 JSON Schema 均采用 `additionalProperties: false`，防止模型传入未知敏感字段。

特别约定：`browser_approval_status` 仅查询批准进度；真正的 approve/deny 只能由用户可信本地 UI 调用独立受保护的内部 API，**没有 MCP 形式的 approve 工具**。`browser_artifact_read` 必须校验原会话归属、blob 生命周期与审计权限。

对于 `browser_type_text`，`strategy=auto|keyboard|ime` 是用户意图；返回结果必须记录 backend 实际策略。若显式请求 `ime` 而会话不支持 `input.ime`，应返回 `UNSUPPORTED_CAPABILITY`，不能悄悄换成 Unicode 输入。`browser_scroll` 的 `unit=pixel|line` 应在 OS adapter 进行一致性映射，但不得宣称不同操作系统的物理滚轮输出完全一致。`browser_wait_for` 使用 `query={role,name,match}`，避免直接使用 stale AX nodeId 无限等待。

所有工具响应结果及 session schema 均不得以 arbitrary `args` 绕过权限。对于扩展动作，先定义新的明确 schema 和 capability，再实现后端。
